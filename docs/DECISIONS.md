# Decisions (ADR)

## ADR-001 — Форк GPL-монолита, а не закрытая оболочка на GPUI

**Статус:** принято.

**Контекст:** `gpui` — Apache-2.0, но `editor`, `project`, `workspace`, `ui`,
`language`, `lsp`, `dap`, `rope`, `text` — GPL. Закрытый шелл потребует
переписать весь стек.

**Решение:** форк Zed, open-core. Клиент — GPL. Проприетарная
дифференциация — только sidecar-процессы.

**Следствия:** нужно публиковать исходники форка при распространении; нельзя
в Mac App Store (DRM против GPLv3); экономия 3–5x по срокам относительно
варианта «с нуля».

## ADR-002 — PHP-интеллект: PHPantom, затем phpactor, Intelephense — opt-in

**Статус:** принято.

**Контекст:** Intelephense даёт лучший UX, но проприетареy и запрещает
редистрибуцию; rename и code actions — только в платной версии. Phpactor —
MIT, но автор предупреждает о производительности. PHPantom — MIT, Rust,
полный LSP, 38 контрибьюторов, но 8 месяцев от роду (pre-1.0).
PHPStan/Psalm — batch, не LSP.

**Решение:**

1. PHPantom — основной сервер.
2. phpactor — вторичный, для зрелых code actions и move-class.
3. Intelephense — по желанию пользователя со своей лицензией. Никогда не
   бандлить.

**Следствия:** нужен переключатель серверов в настройках и fallback при
падении. Никакой зависимости от платного ключа в базовой поставке.

## ADR-003 — Не писать свой анализатор PHP в фазах 0–5

**Статус:** принято.

**Контекст:** собственный type inference уровня PhpStorm — 1–3 года.

**Решение:** фаза 6 — форк PHPantom (MIT) или встраивание крейтов Mago за
`tower-lsp`. Не использовать внутренности PHPStan/Psalm как runtime-oracle:
нестабильные API, полный проход на каждый файл, 1–2 ГБ.

**Следствия:** качество типов ограничено PHPantom до фазы 6; это приемлемо,
потому что 80% ежедневных задач покрываются LSP.

## ADR-004 — Панели только через форк

**Статус:** принято.

**Контекст:** Extension API не умеет кастомный UI; визуальный RFC — черновик.

**Решение:** панели — GPL-крейты + регистрация в `initialize_panels`.

**Следствия:** каждый форк-релиз требует ребейза; поэтому патчи ядра
минимальны и регистрационные.

## ADR-005 — Дисциплина upstream

**Статус:** принято.

**Решение:** трекаем стабильные теги (не `main`), ребейз раз в месяц,
security-фиксы еженедельно, `git rerere`, patch queue, CI против каждого
нового тега. Ветка форка живёт отдельно от `vendor/zed`.

**Следствия:** ~1–2 инженеро-дня в месяц на апстрим; при патчах ядра >10k LOC
налог становится неприемлемым.

## ADR-006 — Свой бренд, никаких ассетов JetBrains

**Статус:** принято.

**Решение:** собственное имя, иконки, тема. Feature parity, layout, горячие
клавиши — можно. Логотипы, скриншоты, иконки, «New UI» 1:1, упоминание
PhpStorm в названии/домене — нельзя. Формулировка «PhpStorm-like» с
дисклеймером допустима.

**Следствия:** нужен дизайнер и, перед релизом, freedom-to-operate review.

## ADR-007 — Gutter-run тестов через runnables, не через свой протокол

**Статус:** принято.

**Контекст:** Zed уже умеет `task` + `tags` + runnables.

**Решение:** задачи PHPUnit/Pest с тегами; парсинг JUnit XML для статусов и
coverage. Свой протокол — только если runnables не хватит.

**Следствия:** меньше патчей ядра; ограничения runnables принимаем.

## ADR-008 — Секреты вне settings

**Статус:** принято.

**Решение:** пароли БД, SFTP и токены — в macOS Keychain; в JSON только
ссылки на ключи. Никаких секретов в репозитории и в логах.

**Следствия:** нужен крейт/keychain-обёртка и явный UX «сохранить пароль».
